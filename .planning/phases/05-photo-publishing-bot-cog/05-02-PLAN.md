<objective>
Build the atomic cross-repo commit transport: a pure `core/github_publish.py` module that publishes image(s) + a `gallery.json` entry, or removes a message's photos, as ONE commit against the website repo via the GitHub Git Data API (blobs -> tree -> commit -> ref). This is the second half of the publish happy path and the whole of removal's write side.

Purpose: The Contents API commits only one file per request, which would split image and `gallery.json` into two commits (two Pages builds, a broken-tile window) — violating D-16. The Git Data API is the only transport that commits both atomically AND deletes files (`sha: null`), which PyGithub cannot do cleanly. Isolating this in a pure module keeps the network/commit logic unit-testable with mocked HTTP, separate from Discord.

Output: `nocturna-bot/core/github_publish.py` with `publish_message(...)` and `remove_message(...)`, serialized by an `asyncio.Lock` with retry-on-conflict, plus a passing `tests/test_github_publish.py` that asserts the API call sequence and tree payloads with `requests` mocked.
</objective>

<reference_patterns>
Verified from 05-RESEARCH.md — use directly.

Atomic commit sequence (Pattern 3, VERIFIED against docs.github.com REST git). Headers: `Authorization: Bearer {GITHUB_PAT}`, `Accept: application/vnd.github+json`. Repo = `config.WEBSITE_REPO`, branch = `config.WEBSITE_BRANCH`.
1. GET `/repos/{repo}/git/ref/heads/{branch}` -> parent commit sha
2. GET `/repos/{repo}/git/commits/{parent_sha}` -> base tree sha
3. GET `/repos/{repo}/contents/{WEBSITE_GALLERY_JSON}?ref={branch}` -> base64 -> `json.loads` current array (tolerate `[]` AND a populated array)
4a. PUBLISH: for each webp, POST `/git/blobs` `{content: b64, encoding: "base64"}` -> blob sha; tree entries = one `{path: "public/gallery/<name>", mode: "100644", type: "blob", sha: blob_sha}` per image PLUS `{path: WEBSITE_GALLERY_JSON, mode: "100644", type: "blob", content: <new json string>}`
4b. REMOVE: tree entries = `{path: WEBSITE_GALLERY_JSON, mode: "100644", type: "blob", content: <filtered json string>}` PLUS one `{path: "public/gallery/<name>", mode: "100644", type: "blob", sha: None}` per removed file (`sha: null` DELETES the file)
5. POST `/git/trees` `{base_tree: base_tree_sha, tree: [...]}` -> new tree sha
6. POST `/git/commits` `{message: <D-17 message>, tree: new_tree_sha, parents: [parent_sha]}` -> commit sha
7. PATCH `/repos/{repo}/git/refs/heads/{branch}` `{sha: commit_sha}` — a PAT push here triggers deploy.yml `on: push` (GITHUB_TOKEN would NOT).

gallery.json write rules (VERIFIED Phase 4 contract):
- entry shape `{ file, caption?, width, height, date }`; identity = `file`
- OMIT the `caption` key entirely when there is no caption (never `"caption": ""`)
- serialize with `json.dumps(array, ensure_ascii=False, indent=2)` (matches shipped 2-space formatting; keeps non-ASCII captions readable and escaped)
- append order does not matter — the site sorts newest-first by `date` at build

Removal derivation (D-14): a message's files are exactly the `gallery.json` entries whose `file` matches the `{msgID}` segment of the `{YYYYMMDD}-{message.id}-{index}.webp` convention. Match the EXACT middle segment (split on `-`), not a naive substring, to avoid snowflake-prefix collisions.

Commit messages (D-17, NO Discord usernames): publish -> `gallery: publish N photos (discord msg <id>)`; remove -> `gallery: remove N photos (discord msg <id>)`.

Concurrency (Pattern 3 / Pitfall 4): wrap the whole read-modify-commit-ref in an `asyncio.Lock` (single-process bot); on a 409/422 "ref moved / not a fast forward", re-fetch the ref and rebuild, retrying a few times with backoff (D-18).

Transport dep: `requests` is ALREADY in requirements.txt — reuse it. Do NOT add PyGithub or GitPython.
</reference_patterns>
