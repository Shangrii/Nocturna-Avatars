## Summary

Phase 3.1 is a pure front-end addition to an already-deployed Astro static site. The codebase is disciplined and consistent — one script pattern (`astro:page-load`), one modal pattern (`.dc-overlay`/`.dc-modal` with the WR-01 hidden-before-transition guard), one token system (`@theme` in `theme.css`). All required design tokens already exist in `theme.css`. The `chrome.ts` module-flag guard pattern is the most important thing to replicate correctly in `cart.ts`.

The existing `services.json` has 5 empty catalog categories (the 5th being `accessories`); Phase 3.1 replaces them with 4 populated ones and adds `id` + `repeatable` fields to each item. `CatalogSection.astro` renders clean `<li class="catalog-row">` flex rows that accept a third column by adding `gap` and a cart-control element. `ServicesPage.astro` has exactly two `<section>` blocks — the cart components slot after both.

**Primary recommendation:** Extend `CatalogSection.astro` directly (no wrapper needed — the `enableCart` prop approach is minimal friction), write all new styles in scoped `<style>` blocks plus a new `src/styles/cart.css` for shared drawer/pill/modal CSS, and mirror `chrome.ts` exactly for the module-flag guard and WR-01 open/close pattern.

## 3. chrome.ts — Modal & Module-Flag Pattern

**File:** `src/scripts/chrome.ts`

### Module-level flags

```typescript
let langDocListenersBound = false;   // guards lang dropdown document listeners
let modalDocListenersBound = false;  // guards Discord modal Escape listener
let scrollHandler: (() => void) | null = null;  // removed/re-added each nav to prevent stacking
```

### `initDiscordModal()` — exact open/close signatures

There is no exported `openModal` / `closeModal`. The functions are closures inside `initDiscordModal()`. The pattern:

```typescript
// Open
overlay.removeAttribute('hidden');          // WR-01: remove [hidden] BEFORE .active
overlay.classList.add('active');
overlay.setAttribute('aria-hidden', 'false');
document.body.style.overflow = 'hidden';
firstFocusable?.focus();                    // focus trap

// Close
overlay.classList.remove('active');
overlay.setAttribute('aria-hidden', 'true');
document.body.style.overflow = '';
lastFocus?.focus();                         // return focus to trigger
overlay.addEventListener('transitionend', () => overlay.setAttribute('hidden', ''), { once: true });
// WR-01: re-add [hidden] AFTER the CSS fade completes, not before
```

### Trigger selectors

- `'.dc-trigger'` → opens Discord modal (querySelectorAll on each `page-load`)
- `'[data-dc-dismiss]'` → closes Discord modal
- Backdrop click: `e.target === overlay` check on overlay click listener

### Escape key handler

```typescript
if (!modalDocListenersBound) {
  modalDocListenersBound = true;
  document.addEventListener('keydown', (e) => {
    const live = document.querySelector<HTMLElement>('[data-dc-overlay]');
    if (e.key === 'Escape' && live?.classList.contains('active')) {
      live.classList.remove('active');
      live.setAttribute('aria-hidden', 'true');
      document.body.style.overflow = '';
      live.addEventListener('transitionend', () => live.setAttribute('hidden', ''), { once: true });
      // NOTE: the Escape close in chrome.ts does NOT return focus (intentional omission);
      // cart.ts SHOULD return focus (better a11y — return focus to lastFocus)
    }
  });
}
```

### astro:page-load mounting

```typescript
function init(): void {
  initNav();
  initLangSwitch();
  initDiscordModal();
}
document.addEventListener('astro:page-load', init);
```

### Critical pattern for cart.ts to mirror

Module flag variable naming convention: `{feature}DocListenersBound = false`.

The per-element event listeners (row buttons, pill click, drawer close) are safe to re-bind each `astro:page-load` because `ClientRouter` provides fresh DOM nodes. Only document-level listeners (Escape, backdrop click) need the flag guard.

## 4. Lang / i18n Runtime Access

### At build time (Astro components)

The `lang` prop (`'es' | 'en'`) is passed from the page resolver down through `ServicesPage.astro` → `CatalogSection.astro`. This is the authoritative source for rendering bilingual strings in templates.

### At runtime (cart.ts — client-side JS)

`BaseLayout.astro` sets `<html lang={lang}>`. Client-side JS can read:

```typescript
const lang = document.documentElement.lang as 'es' | 'en';
// Returns 'es' on /es/servicios, 'en' on /en/services
```

There is **no** `data-lang` attribute on `<body>`. The `<html lang>` attribute is the only runtime signal.

**Validation:** `BaseLayout.astro` line 47: `<html lang={lang}>` — confirmed.

### Pattern used in UI-SPEC for runtime bilingual copy

The cart pill label uses `lang` attributes on child spans (not JS):

```html
<span lang="es">servicios → Abrir Ticket</span>
<span lang="en" hidden>services → Open Ticket</span>
```

But cart.ts needs to generate clipboard text and dynamic aria-labels. It should read `document.documentElement.lang` once at `initCart()` call time:

```typescript
function initCart(): void {
  const lang = (document.documentElement.lang || 'en') as 'es' | 'en';
  // use lang for all dynamic copy generation
}
```

## 8. Script Loading Pattern

**Files:** `src/layouts/BaseLayout.astro`, `src/scripts/chrome.ts`

### Pattern in use

All client-side scripts use `<script>` tags with ESM imports in Astro component frontmatter-sibling `<script>` blocks:

```astro
<script>
  import '../scripts/chrome.ts';
</script>
<script>
  import '../scripts/motion/index.ts';
</script>
```

Astro's Vite bundler treats these as ES modules — no `type="module"` attribute needed (Astro adds it). Scripts are bundled and deduplicated.

### Key pattern: `astro:page-load` instead of `DOMContentLoaded`

```typescript
document.addEventListener('astro:page-load', initFn);
```

This fires on both the initial load AND every ClientRouter navigation. Per-element listeners re-bind to fresh DOM nodes each time. Document-level listeners are guarded with module-flag booleans.

### Where to load cart.ts

Option A (recommended): Inline `<script>` in `ServicesPage.astro` — scopes the script to the services page only. Astro will only bundle it into the services page chunk.

Option B: Load in `BaseLayout.astro` — runs on every page. Wasteful since the cart is services-page-only.

**Use Option A.**

### Module-flag guard template for cart.ts

```typescript
let cartDocListenersBound = false;

function initCart(): void {
  bindCartRowControls();    // per-element, safe to re-bind
  bindPillClick();          // per-element
  bindDrawerClose();        // per-element
  syncCartUI();             // re-render from persistent module state

  if (!cartDocListenersBound) {
    cartDocListenersBound = true;
    bindEscapeKey();
    bindBackdropClick();
  }
}

document.addEventListener('astro:page-load', initCart);
```

## 9. Integration Risks & Landmines

### Risk 1: `.catalog-row` flex layout overflow on mobile

**What:** The current `.catalog-row` is `justify-content: space-between` with two columns (name + price). Adding a third cart-control column may overflow at narrow widths without explicit `gap` and `min-width: 0` on the name column.

**Fix:** The UI-SPEC already addresses this with `catalog-row--interactive { gap: var(--space-sm) }` and `catalog-row__name { flex: 1; min-width: 0; overflow: hidden; text-overflow: ellipsis; }`. The price column hides at `max-width: 480px` — price still shows in the drawer.

**Landmine:** The current `.catalog-row` CSS lives in a scoped `<style>` block in `CatalogSection.astro`. The new `.catalog-row--interactive`, `.catalog-row__cart-btn`, `.catalog-row__qty` styles must also live there (or in a new global cart.css). Scoped Astro styles do NOT apply to child components or dynamically injected HTML — since cart controls are in the Astro template (not injected by JS), scoped styles work fine.

### Risk 2: `astro:page-load` fires on every soft navigation — cart state persists across navigations

**What:** Cart state is module-scoped (intentional — D-06). When navigating away from `/servicios` and back, `initCart()` fires again and calls `syncCartUI()`. The cart state (the `Map`) persists in module scope because the JS module is not re-evaluated on ClientRouter navigation. This is the desired behavior.

**Landmine:** `syncCartUI()` must re-query DOM elements by selector each time (fresh DOM after swap). It cannot close over stale node references from a previous navigation. This is the same requirement as `chrome.ts`'s Escape handler which calls `document.querySelector('[data-dc-overlay]')` fresh each time.

### Risk 3: `[hidden]` attribute vs. `display: flex` conflict (WR-01)

**What:** `.dc-overlay` has `display: flex` in its base rule and `display: none` in the `[hidden]` override. The `[hidden]` rule must have higher specificity than the base rule to win. In `chrome.css`:

```css
.dc-overlay { display: flex; ... }
.dc-overlay[hidden] { display: none; }  /* attribute selector wins over class — specificity OK */
```

The cart backdrop uses `display: none` for `[hidden]` as well. The cart drawer uses `[hidden]` to gate display. Cart pill uses `[hidden]` attribute natively (`<button hidden>`). All of these must follow the same remove-hidden-before-active pattern. **Do not add `.active` while `[hidden]` is still set.**

### Risk 4: `transitionend` fires per-property — multiple events per element

**What:** When the `.dc-overlay` has `transition: opacity 0.35s ease` AND `.dc-modal` inside has `transition: transform 0.35s` — the overlay's `transitionend` fires ONCE for the `opacity` property. If the drawer has two transitioned properties (`transform` on the panel, `opacity` on the backdrop), each fires a `transitionend`. Use `{ once: true }` on the listener and listen on the specific element that triggers the meaningful end-of-transition.

**Fix:** Listen to `transitionend` on the drawer panel itself (`cart-drawer`) for the `transform` property:
```typescript
drawer.addEventListener('transitionend', (e) => {
  if (e.propertyName === 'transform') drawer.setAttribute('hidden', '');
}, { once: true });
```

### Risk 5: z-index collision between drawer (z-960) and nav (z-1000)

**What:** The drawer panel is `z-index: 960`, which is below the nav at `z-index: 1000`. The drawer will slide in BEHIND the nav at the top. This is correct — the nav should stay visible above the drawer. The UI-SPEC confirms this is intentional.

**Landmine:** The nav hide-on-scroll (`nav--hidden` class, `transform: translateY(-100%)`) is still active. When the drawer is open and the user scrolls, the nav hides. This is acceptable behavior — the drawer covers most of the page, scrolling is unlikely.

### Risk 6: Focus trap implementation

**What:** The UI-SPEC requires focus trap in both the drawer and cart modal. `chrome.ts` does NOT implement a full focus trap — it only calls `firstFocusable?.focus()` on open and `lastFocus?.focus()` on close. A real focus trap also intercepts Tab/Shift+Tab to cycle within the container.

**Decision needed (Claude's discretion):** Implement a minimal focus trap (query all focusable elements inside the container, intercept Tab keydown, cycle with modulo arithmetic) — or accept the simplified version from `chrome.ts`. For the cart drawer which contains a list + CTA button + close button, a minimal trap is ~20 lines. Recommended: implement it for the drawer and reuse for the modal.

### Risk 7: `packages.addons[]` typo in existing data

**What:** In the current `services.json`, one add-on has a typo: `"Expressions personalizadas"` (should be "Expresiones personalizadas"). When this add-on is added as a catalog item, use the corrected spelling.

### Risk 8: CatalogSection.astro renders `item.price` directly without `$` prefix

**What:** The current component renders `{isCotizar ? 'Cotizar' : item.price}` — no currency symbol. The catalog rows show the raw price string. The UI-SPEC drawer and modal show `$N USD`. Cart.ts must add the `$` and `USD` suffix when displaying prices in the drawer/modal; the row itself continues to render the raw `item.price` (which is `"99"`).

**Implication:** Services with `price === "cotizar"` are excluded from the numeric total but shown in the drawer/modal as "Cotizar".

### Risk 9: `addonsNote` data usage

**What:** `ServicesPage.astro` currently reads `servicesData.packages.addonsNote` and renders it under the add-ons grid. When the add-ons block is removed (D-03), the `addonsNote` variable becomes unused. The TypeScript compiler may not warn about unused variables in Astro frontmatter, but it is clean practice to remove the assignment as well.
