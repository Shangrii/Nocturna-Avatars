# Phase 10.1 Plan 12: Self-Hosted View Counter Summary

**Tiny standalone FastAPI view-counter (`counter_app.py` on loopback 8771) serving `GET /api/views/<slug>?hit=1 → {"count": n}` from a hashed-IP-deduped sqlite `view_counts` store, with CORS for the public site and a sibling systemd + Caddy `/api/views` deploy — no third party (D-25).**

## Accomplishments
- `core/db.py`: `view_counts` + `view_dedup` tables with `init_view_counts()`, `get_view_count()`, `increment_view()` — the increment is a no-op inside a 6h per-slug+ip_hash window so a reload can't inflate the count; only a SHA-256 hash of the IP is stored, never the raw address.
- `app/counter_app.py`: a minimal FastAPI app (deliberately separate from `app.main`) exposing exactly the contract `ViewCounter.astro` calls — validates the slug `[a-z0-9-]+` (404 otherwise), increments off the event loop on `hit=1`, returns `{"count": 0}` for an unknown-but-well-formed slug (never 500), and allows CORS for `config.WEBSITE_BASE_URL` (+ www/non-www variant) GET only. Binds loopback `127.0.0.1:8771`.
- `tests/test_counter_app.py`: 7 tests covering increment, read-only, dedup no-op, unknown-slug→0, malformed-slug reject, IP-hash storage, and CORS. Full bot suite: **552 passed**.
- Deploy artifacts: `nocturna-view-counter.service` (sibling unit, uvicorn `app.counter_app:app` loopback 8771), Caddy `handle /api/views/*` → 8771 with per-IP `rate_limit`, and a new `EDITOR_DEPLOY.md §8` runbook — no secret literals anywhere.

## Decisions Made
- **IP as hash only + 6h dedup window** — satisfies the privacy (T-10.1-12-02) and reload-inflation (T-10.1-12-01) mitigations without a raw-IP column.
- **Separate app, not a route on `app.main`** — keeps the public unauthenticated counter fully isolated from the admin app's OAuth/session/config-guard machinery (per the plan's explicit "never touches main.py").
- **Malformed slug → 404, unknown slug → {count:0}** — the client always gets a clean integer and hides the counter on any failure (UI-SPEC graceful degradation).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] systemd `ProtectHome=read-only` would block the sqlite write**
- **Found during:** Task 2 (deploy artifacts)
- **Issue:** The plan said to mirror `nocturna-editor-admin.service`, which uses `ProtectHome=read-only`. That unit writes nothing to disk (it commits to GitHub), but the view counter WRITES the shared sqlite db, which lives under `$HOME/nocturna-bot`. Copying the hardening verbatim would make every `increment_view` write fail at runtime.
- **Fix:** Added `ReadWritePaths=/home/YOUR_USER/nocturna-bot` to carve out the checkout dir while keeping `ProtectHome=read-only` for the rest of `$HOME`; documented the DB_PATH-elsewhere case in the unit comment and §8.1.
- **Files modified:** `../nocturna-bot/deploy/nocturna-view-counter.service`
- **Verification:** Documented + reasoned; live start is a human deploy step (like 10-11).
- **Committed in:** `1702a6e` (Task 2 commit)

**2. [Rule 1 - Bug] Caddy bare `reverse_proxy` fallback would double-route `/api/views/*`**
- **Found during:** Task 2 (Caddy snippet)
- **Issue:** The existing snippet ends in a bare `reverse_proxy 127.0.0.1:8770`. Adding a `handle /api/views/*` block alongside a non-`handle` catch-all proxy is a Caddy footgun — the bare proxy also matches `/api/views/*`, so requests could be routed to both apps.
- **Fix:** Wrapped the admin-app proxy in a catch-all `handle { reverse_proxy 127.0.0.1:8770 }` so it is mutually exclusive with the `/api/views` handle.
- **Files modified:** `../nocturna-bot/deploy/Caddyfile.snippet`
- **Verification:** `caddy validate` is a human deploy step; structure now uses mutually-exclusive `handle` blocks (the correct Caddy idiom).
- **Committed in:** `1702a6e` (Task 2 commit)
