# Phase 10.1: Code Review Report

**Reviewed:** 2026-07-16T00:00:00Z
**Depth:** standard
**Files Reviewed:** 39
**Status:** issues_found

## Summary

This phase ships the standalone per-editor "link-in-bio" pages driven by editor-controlled theme/block data from `editors.json` (documented, repeatedly, as *untrusted at build time*). The render-side XSS discipline for **text content** is genuinely solid: every string field flows through Astro `{}` auto-escaping, no `set:html` touches editor data (the one `set:html` in `SocialIconRow` inlines a fixed first-party SVG map, not editor data), and all client scripts write untrusted values via `textContent` / `setAttribute` only. The lightbox editor-credit href is regex-guarded (`EDITOR_SLUG_RE`), the legacy redirect stub uses a build-time `define:vars` literal with no runtime interpolation, numeric theme knobs are clamped, `bgMedia` is extension-gated, and the font/effects/badge/button enums are whitelisted. Presence/view-counter fetches degrade silently with no leaked error text.

The gaps are in the **non-text** editor-controlled surfaces that the render layer claims to defend but does not: outbound link **href schemes** are passed through unguarded (the one field type that can execute script), and the **color theme tokens** are emitted into an inline `style` object without any CSS-value sanitization, contradicting the layout's own stated "values are re-clamped/whitelisted" posture. Both rely entirely on a single upstream bot-side gate that this render layer is explicitly supposed to back-stop. One correctness bug (multiple portfolio blocks break lightbox indexing) and several quality items round out the review.

## Critical Issues

### CR-01: Editor link `href` values are not scheme-guarded render-side — `javascript:`/`data:` URL is stored XSS

**File:** `src/components/editor-shell/LinkButton.astro:43`, `src/components/editor-blocks/LinksBlock.astro:30-35`, `src/components/editor-shell/SocialIconRow.astro:112-118`
**Issue:** All three components bind an editor-supplied URL directly as `href={url}` and rely solely on the comment "https-only, validated upstream (10-02 model)". Astro auto-escaping prevents HTML-attribute breakout but does **not** neutralize dangerous URL schemes — `<a href="javascript:...">` still executes on click, and `rel="noopener noreferrer nofollow"` does nothing to stop it. `editors.json` is explicitly untrusted at build time, so if the single bot-side validator ever misses a case (or is bypassed for a manually-committed entry), a `javascript:` / `data:text/html` URL in `links[]`, a block's `items[].url`, or `socials[].url` becomes a clickable script-execution vector on a public, `index,follow` page.

Note `SocialIconRow` does not help here: `new URL('javascript:alert(1)')` parses successfully with `hostname === ''`, falls through to the `generic` platform, and is still emitted with the raw `javascript:` href.

This is the one untrusted field type that can execute script, yet it is the only one the render layer leaves undefended — every sibling value (numerics, `bgMedia`, font, effects, badges, button enums) is clamped/whitelisted render-side. The render layer is described in-file as "the render-side half of the defense"; that half is missing for href schemes.
**Fix:** Add a shared render-side scheme guard and drop any link that fails it (mirroring the existing per-entry filters):
```ts
// src/lib/url.ts (new) — or inline in each component
export function safeHref(url: unknown): string | null {
  if (typeof url !== 'string' || url.length === 0) return null;
  try {
    const u = new URL(url, 'https://x.invalid'); // base handles protocol-relative
    return u.protocol === 'https:' || u.protocol === 'http:' ? url : null;
  } catch {
    return null;
  }
}
```
Then filter with it in `LinksBlock` (`item.url` guard), the `links` filter in `pages/e/[slug].astro:80-83`, and `SocialIconRow`'s `resolved` map (`if (safeHref(item.url) === null) return null;`). `LinkButton` receives already-filtered URLs, so guarding at the route filter covers it.

## Warnings

### WR-01: Color theme tokens are emitted into the inline `style` object with no CSS-value sanitization (CSS-declaration injection)

**File:** `src/layouts/EditorLayout.astro:77-92`
**Issue:** `bg`, `surface`, `accent`, `text`, `textMuted`, and `tint` are placed into the `themeStyle` object after only a `typeof === 'string'` check. Astro serializes a style object as `prop:value;` pairs and HTML-attribute-escapes the final string, which escapes `"`/`<`/`>`/`&` but **not** `;` or `:`. A value such as `#000; background-image: url(https://attacker.example/beacon.gif)` therefore injects an extra CSS declaration onto the `.editor-page` root element. The file's own header comment claims "editor-controlled values only ever fill VALUES ... numerics are re-clamped" — but unlike the numerics (`clampNum`) and `bgMedia` (`.replace(/["'\\()]/g, '')`), the color strings get no treatment at all, directly contradicting the stated theme-injection defense and the phase's explicit review priority ("verify they're clamped/whitelisted ... can't smuggle CSS").

Impact is bounded (inline style = one element, no selector/`@import`/script injection), but it still permits an editor to load an arbitrary external resource (privacy beacon / silent tracking) from a public page purely via committed data, and it is defense-in-depth the layout advertises but does not deliver.
**Fix:** Validate each color token against a conservative pattern before emission and fall back to the default on failure, e.g.:
```ts
const COLOR_RE = /^(#[0-9a-fA-F]{3,8}|rgba?\([\d.,\s%]+\)|hsla?\([\d.,\s%]+\)|[a-zA-Z]+|transparent)$/;
const safeColor = (v: unknown, dflt: string) =>
  typeof v === 'string' && COLOR_RE.test(v.trim()) ? v.trim() : dflt;
// '--theme-bg': safeColor(theme.bg, '#0a0c14'), etc.
```
At minimum, reject any color value containing `;`, `{`, `}`, or `url(`.

### WR-02: Multiple `portfolio` blocks produce colliding `data-index`, so the lightbox opens the wrong image

**File:** `src/components/editor-blocks/PortfolioBlock.astro:129-138`, `src/scripts/gallery.ts:713-728`
**Issue:** `gallery.ts` builds its `entries[]` array from **all** `[data-gallery-tile]` nodes in document order (global 0..N-1), but `openLightbox` resolves the clicked tile via `Number(tile.dataset.index)`. `PortfolioBlock` sets `data-index={i}` where `i` restarts at 0 **per block**. The schema (`EditorBlock[]`) permits more than one `portfolio` block, so on any editor page with two portfolio blocks, the second block's tiles carry `data-index` 0..m-1 while their true positions in `entries[]` are offset by the first block's length. Clicking a tile in the second block opens the wrong photo (an earlier block's image).
**Fix:** Don't trust a per-block index. Either compute the index at click time from the tile's position among all tiles, or stop emitting `data-index` and derive it in `gallery.ts`:
```ts
const tiles = Array.from(document.querySelectorAll<HTMLElement>('[data-gallery-tile]'));
tiles.forEach((tile, idx) => tile.addEventListener('click', () => openLightbox(overlay, idx)));
```

### WR-03: `EditorLayout` renders a redundant, always-occluded background-media layer that re-downloads the editor's media

**File:** `src/layouts/EditorLayout.astro:130-134` + `src/styles/editor-theme.css:96-104`
**Issue:** `EditorLayout` emits `--theme-bg-media: url("<media>")` and a `.editor-bg__media` layer that sets `background-image: var(--theme-bg-media)`. The route `pages/e/[slug].astro` then renders its **own** `.e-bg` layer with an opaque `background-color: var(--theme-bg)` that (per its own comment) "fully occludes the layout's fallback bg layer" and renders the same media a second time as a real `<video>`/`<img>` element. The layout's CSS background layer is therefore never visible, yet the browser still fetches the referenced media (potentially a large gif/webm) — the media is downloaded twice per page load. This is dead visual output plus a wasted fetch, and the two layers duplicating "media + tint + scrim" markup is a maintenance trap.
**Fix:** For `/e/` pages the route owns the media layer; drop the `.editor-bg__media` background-image usage from the always-occluded `EditorLayout.editor-bg` (or don't emit `--theme-bg-media` at the layout level), leaving a single media layer of record in the route.

## Info

### IN-01: `editor-theme.css` header comment says "13 --theme-* tokens" but 12 are defined and emitted

**File:** `src/styles/editor-theme.css:5` (and `:56-70`)
**Issue:** The banner comment states "the 13 --theme-* tokens", while the `:root` block defines 12 (`bg`, `bg-media`, `overlay`, `blur`, `tint`, `surface`, `accent`, `text`, `text-muted`, `font`, `btn-style`, `btn-shape`) — matching `EditorLayout`'s "12 `--theme-*`" comment and its 12-key `themeStyle` object. Documentation drift; harmless but misleading.
**Fix:** Change "13" to "12" in the header comment.

### IN-02: `ImageBlock.astro` is dispatched but was not in the review set

**File:** `src/components/editor-blocks/BlockRenderer.astro:23,40`
**Issue:** `BlockRenderer` imports and renders `ImageBlock` for `block.type === 'image'` (schema field `image` has editor-controlled `src`/`alt`), but `ImageBlock.astro` was not included in the reviewed file list, so its handling of the editor `src` could not be verified. An `<img src="javascript:...">` is inert (no script execution), so this is not an XSS concern, but the `src` is an editor-controlled URL like the ones flagged in CR-01 and should get the same treatment if it renders as anything clickable/loadable.
**Fix:** Confirm `ImageBlock` renders `src` only as an `<img>`/escaped attribute; consider a resource-scheme guard consistent with the CR-01 fix.

### IN-03: `viewcounter.ts` module-global `fired` short-circuits all counters if the first lacks a slug

**File:** `src/scripts/editor/viewcounter.ts:15-24`
**Issue:** `ping()` sets the module-level `fired = true` **before** the `slug` guard. `boot()` runs `els.forEach(ping)`, so if the first `[data-viewcount]` element had no slug it would set `fired` and silently prevent every later counter from pinging. There is exactly one `ViewCounter` per editor page today, so this cannot trigger in practice, but the ordering (flag before validating this element is actually pingable) is fragile.
**Fix:** Move `if (!slug) return;` above `fired = true;`, or scope the once-guard per element rather than per module.

### IN-04: `effects.ts` particle canvas leaks its `resize`/`visibilitychange` listeners

**File:** `src/scripts/editor/effects.ts:150-158`
**Issue:** `initParticles` adds `window` `resize` and `document` `visibilitychange` listeners (plus the RAF loop) that are never removed. Because editor pages have no `ClientRouter` / view transitions, the module runs once and the page is torn down by a full navigation, so nothing accumulates in practice — but the listeners and canvas are unbounded if this engine is ever reused on a soft-navigated surface. Performance is out of v1 scope; noted only as a cleanliness/robustness item.
**Fix:** If the effects engine is later mounted under view transitions, track and remove these listeners (and `cancelAnimationFrame`) on teardown.
