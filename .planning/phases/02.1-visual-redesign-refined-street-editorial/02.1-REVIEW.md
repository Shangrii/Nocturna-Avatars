# Phase 02.1: Code Review Report

**Reviewed:** 2026-06-30
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

This phase delivered the Refined Street Editorial re-skin: Tailwind v4 CSS-first integration, an ink/paper token system, revised chrome and section components, a 404 page, Terms column, and the hero shader rework. The overall architecture is solid — the token aliasing bridge is correct, the motion lifecycle is well-structured, and most a11y scaffolding is in place. However, there are seven critical defects spanning accessibility violations (modal missing focus management and ARIA labelling, dialog role misuse), a real XSS surface in the Discord modal's `set:html`, a CSS specificity collision that silently strips the `.hero-cta:hover` lift, a choreography mismatch (CSS uses `data-teaser-body` as a descendant selector but the JS also targets that attribute and there is no guarantee the component emits it), and a motion-init double-initialization risk under Astro's ClientRouter. These need to be fixed before this code ships.

## Critical Issues

### CR-01: Discord modal `set:html` is an XSS surface

**File:** `src/components/DiscordModal.astro:36`

**Issue:** `<h3 class="dc-title" set:html={t.modalTitle}></h3>` renders the `modalTitle` dictionary value as raw HTML. The comment says "the value is a static dictionary string, never untrusted input," but the i18n system loads JSON at build time from `src/i18n/*.json`. If any part of the i18n pipeline is ever extended to pull external data (bot posts, CMS), or if a developer edits nav.json and includes angle-bracket characters without realizing this field is rendered as HTML, the result is stored XSS served from the site to every visitor. The `<em>` emphasis the comment refers to is purely decorative styling — it does not require raw HTML injection; it can be expressed as two text nodes with conditional markup instead. The risk is structural: the code is currently safe, but has zero defense-in-depth; one edit to nav.json can compromise the site.

**Fix:** Replace `set:html` with explicit conditional markup:
```astro
---
// In DiscordModal.astro frontmatter, split modalTitle in nav.json into
// t.modalTitleBefore / t.modalTitleEm / t.modalTitleAfter
---
<h3 class="dc-title">
  {t.modalTitleBefore}<em>{t.modalTitleEm}</em>{t.modalTitleAfter}
</h3>
```
If splitting the string is undesirable, at minimum validate/sanitize the value in the i18n loader before passing it through `set:html`.

### CR-02: Discord modal dialog is not accessible — missing `aria-labelledby`, focus management, and incorrect `aria-hidden` initial value

**File:** `src/components/DiscordModal.astro:25`

**Issue:** Three compounding a11y failures on the modal element:

1. The `<div role="dialog" aria-modal="true">` has no `aria-labelledby` (or `aria-label`). WCAG 4.1.2 requires dialogs to have an accessible name. Screen readers will announce "dialog" with no context.
2. The modal opens via `overlay.classList.add('active')` and `overlay.setAttribute('aria-hidden', 'false')` (chrome.ts:145), but focus is never moved into the modal. Keyboard and AT users will stay focused on whatever triggered it, meaning keyboard interaction behind the scrim is not trapped and the modal content is unreachable by Tab.
3. On close, focus is not returned to the triggering element. For the FloatingCTA and hero CTA this means focus teleports to the body.

**Fix:**
```astro
<!-- Add aria-labelledby pointing to the h3 -->
<div class="dc-overlay" id="dcOverlay" data-dc-overlay
     aria-hidden="true" role="dialog" aria-modal="true"
     aria-labelledby="dcModalTitle">
  ...
  <h3 class="dc-title" id="dcModalTitle" set:html={t.modalTitle}></h3>
```
```ts
// In chrome.ts initDiscordModal():
let lastFocus: HTMLElement | null = null;

const open = (trigger?: HTMLElement) => {
  lastFocus = trigger ?? document.activeElement as HTMLElement;
  overlay.classList.add('active');
  overlay.setAttribute('aria-hidden', 'false');
  document.body.style.overflow = 'hidden';
  // Move focus into the modal
  const firstFocusable = overlay.querySelector<HTMLElement>(
    'a[href], button:not([disabled]), [tabindex]:not([tabindex="-1"])'
  );
  firstFocusable?.focus();
};

const close = () => {
  overlay.classList.remove('active');
  overlay.setAttribute('aria-hidden', 'true');
  document.body.style.overflow = '';
  lastFocus?.focus();
};
```

### CR-03: `motion/index.ts` — `inited` guard causes motion to never re-initialize after a page swap

**File:** `src/scripts/motion/index.ts:23-27`

**Issue:** The module-scoped `inited` flag is set to `true` on first `initMotion()` and reset to `false` in `teardownMotion()`. However, `teardownMotion()` is registered on `astro:before-swap`, which fires *before* the DOM is replaced. After the swap completes, `astro:page-load` fires, calling `initMotion()` again — this is correct. The bug is that `teardownMotion()` is *not* guaranteed to fire before every `astro:page-load`. Under Astro 7's ClientRouter, if a navigation is interrupted or if the first `astro:page-load` fires on the initial load (before any swap has occurred), `inited` starts as `false`, `initMotion()` sets it to `true`, and that is fine. But if `astro:page-load` fires twice without an intervening `astro:before-swap` (e.g., soft-reload or fallback navigation), `inited` is still `true` from the previous run, and `initMotion()` returns early — leaving the new page without scroll triggers, reveals, or choreography running. Additionally, `teardownMotion()` calls `document.documentElement.classList.remove('motion-ready')` which removes the class that gates reveal animations in CSS; if `initMotion()` is short-circuited, `motion-ready` is never re-added and all `.reveal` elements stay at `opacity:0` forever.

**Fix:** The guard should be reset by `teardownMotion()` to `false` *before* calling destroyers, and the `astro:page-load` handler should not early-return if the previous teardown happened. The safest fix is to drop the `inited` guard in `initMotion()` and instead make each sub-module's init truly idempotent:
```ts
function initMotion(): void {
  // Remove the guard entirely; each sub-module no-ops if already running
  document.documentElement.classList.add('motion-ready');
  initSmoothScroll();
  initReveals();
  initHeroShader();
  initChoreography();
  initTransitions();
}
```
Or, if the guard must remain, ensure `teardownMotion()` synchronously resets it:
```ts
function teardownMotion(): void {
  inited = false; // reset FIRST, before any async teardown
  destroyTransitions();
  // ...
}
```

### CR-04: `.hero-cta:hover` lift is silently overridden by choreography.css specificity

**File:** `src/pages/[lang]/index.astro:275-279` and `src/styles/choreography.css:26-29`

**Issue:** In `index.astro`'s scoped `<style>`, `.hero-cta:hover` sets `transform: translateY(-2px)`. In `choreography.css`, `.hero-cta:hover` (inside `@media (hover: hover)`) also sets `transform: translateY(calc(var(--space-3xs) * -1))` which is `-4px`. Astro scoped styles compile to attribute-scoped selectors (e.g. `.hero-cta[data-astro-cid-xxxx]:hover`) while the global choreography.css rule has no attribute scope. CSS specificity therefore favors the scoped rule. This means the choreography's `-4px` lift rule never applies to the hero CTAs — the scoped `-2px` wins. Additionally, `choreography.css:26` applies the `transform` transition to `.hero-cta`, but `index.astro:271-273` also defines its own `transition` on `.hero-cta` — these two `transition` declarations coexist on the same element, with the scoped one winning, but only the scoped `transition` list is applied (no `box-shadow` step, contrary to the choreography declaration).

This means the choreography module's hover contract for `.hero-cta` is effectively dead code on the landing page, and the two files are silently out of sync.

**Fix:** Either remove the `.hero-cta:hover` rule from `index.astro`'s scoped style and rely entirely on choreography.css, or extract the hero-specific hover values into a global CSS rule (not scoped) that matches choreography.css. The simplest fix:
```css
/* Remove from index.astro <style>: */
/* .hero-cta:hover { background: ...; transform: translateY(-2px); } */

/* Ensure choreography.css's .hero-cta:hover is the single source of truth */
```

### CR-05: `prefersReduced` is evaluated at module parse time — misses runtime changes and SSR

**File:** `src/scripts/motion/motion-prefs.ts:15`

**Issue:** `export const prefersReduced = matchMedia('(prefers-reduced-motion: reduce)').matches;` is evaluated once when the module is first imported. It cannot update if the user changes their OS accessibility setting while the page is open (possible with ClientRouter SPA navigation where the page never hard-reloads). More critically, the `matchMedia()` call is at module scope; in any SSR or prerendering context where this module is imported server-side, `matchMedia` does not exist and the build will throw. Astro 7 with `output: 'static'` does not server-execute client scripts, so this is currently safe — but the pattern is fragile: any future move to hybrid/SSR rendering will break the build.

**Fix:**
```ts
// Evaluate at call time to pick up runtime changes, and guard against SSR:
export function prefersReduced(): boolean {
  if (typeof matchMedia === 'undefined') return true; // safe default in SSR
  return matchMedia('(prefers-reduced-motion: reduce)').matches;
}
```
All call sites (`choreography.ts`, `reveals.ts`, `shader.ts`, etc.) currently use `prefersReduced` as a plain boolean; converting it to a function requires updating those callers.

### CR-06: `--color-paper` token value is identical to `--color-ink-raised` — the warm/cool paper rhythm is lost

**File:** `src/styles/theme.css:44-66`

**Issue:** The design system documentation describes `--color-paper` as "a DARK warm espresso-charcoal — a WARM counterpoint to the COOL navy ink" and claims the two tones are "perceptibly distinct via the warm/cool hue shift (navy L*≈3.4, paper L*≈11.3)." However, the actual token values are:
- `--color-ink`: `#0a0c14` (cool navy, L* ≈ 3.4)
- `--color-ink-raised`: `#10131e` (same hue, slightly lighter navy, L* ≈ 5.1)
- `--color-paper`: `#11141f` (virtually identical to ink-raised)

`#10131e` vs `#11141f` differ by 1 unit on each RGB channel — this is indistinguishable to human vision (delta-E < 1). The description says espresso-charcoal should have warm undertones, but `#11141f` has the same cool blue bias as the ink palette. The paper section will look identical to the ink-raised card background, not like a distinct warm editorial counterpoint. All the `.section--surface` rules that flip foreground colors will apply correctly, but the *background rhythm* — the core editorial principle — is broken at the token level.

**Fix:** Use a genuinely warm dark tone for `--color-paper`. A value like `#18120a` (dark espresso/walnut) or `#1a1410` reads as warm-dark while remaining visually similar in lightness:
```css
--color-paper: #18120a; /* dark espresso-walnut, L* ≈ 6.5, warm brown */
```
This makes the ink/paper alternation perceptible and delivers the "editorial rhythm" the design system promises.

### CR-07: `destroyReveals()` kills ALL ScrollTriggers, not just reveal triggers

**File:** `src/scripts/motion/reveals.ts:103-107`

**Issue:** `destroyReveals()` calls `ScrollTrigger.getAll().forEach((t) => t.kill())` — this kills every ScrollTrigger registered by any module, including choreography triggers tagged with `choreo-marquee` and `choreo-parallax`. The teardown order in `teardownMotion()` is `destroyTransitions → destroyChoreography → destroyHeroShader → destroyReveals → destroySmoothScroll`. Because `destroyReveals()` runs last and kills ALL triggers, it renders `destroyChoreography()`'s selective kill logic completely moot — choreography's own cleanup never finds any triggers left. More dangerously, if the teardown order is ever changed, `destroyReveals()` will wipe choreography triggers while the choreography module still holds stale references to them.

**Fix:** Tag reveal ScrollTriggers with their own ID prefix and kill only those:
```ts
// In initReveals(), tag each ScrollTrigger:
scrollTrigger: { id: `reveal-${i}`, trigger: el, ... }

// In destroyReveals():
export function destroyReveals(): void {
  ScrollTrigger.getAll()
    .filter(t => (t.vars as { id?: string }).id?.startsWith('reveal'))
    .forEach(t => t.kill());
  splits.forEach(s => s.revert());
  splits = [];
}
```

### WR-01: `DiscordModal` has `role="dialog"` but `aria-hidden="true"` initially — these conflict

**File:** `src/components/DiscordModal.astro:25`

**Issue:** The element carries both `role="dialog"` and `aria-hidden="true"` simultaneously in the initial HTML. While the intent is to hide it until opened, `aria-hidden` on an element with an interactive role makes it permanently invisible to AT even after the class change makes it visually visible — AT relies on `aria-hidden` being removed to expose the element. `chrome.ts:145` does call `overlay.setAttribute('aria-hidden', 'false')` on open, so it will work, but the initial markup is semantically wrong: a dialog should not exist in the accessibility tree at all when hidden; the correct approach is `display:none` (which `pointer-events:none; opacity:0` is not — it is still in the accessibility tree with `aria-hidden="true"`, causing a confusing state).

**Fix:** Add `hidden` attribute to the overlay in the initial markup and remove it on open; or use `display:none` and toggle it instead of relying solely on `aria-hidden`:
```astro
<div class="dc-overlay" id="dcOverlay" data-dc-overlay
     hidden aria-hidden="true" role="dialog" aria-modal="true">
```
```ts
// In chrome.ts open():
overlay.removeAttribute('hidden');
overlay.setAttribute('aria-hidden', 'false');

// In chrome.ts close():
overlay.setAttribute('aria-hidden', 'true');
// Use a transitionend listener to add [hidden] after the CSS fade completes
overlay.addEventListener('transitionend', () => overlay.setAttribute('hidden', ''), { once: true });
```

### WR-02: `LanguageSwitcher` uses `aria-haspopup="true"` instead of `aria-haspopup="listbox"` or `"menu"`

**File:** `src/components/LanguageSwitcher.astro:38`

**Issue:** `aria-haspopup="true"` is equivalent to `aria-haspopup="menu"` per the ARIA spec, and the component does use `role="menu"` and `role="menuitem"` on the list/options, so this is internally consistent. However, the menu items are `<a>` elements (links, not actions), and using `role="menuitem"` on a link overrides its native link semantics and removes the expected AT announcement of "link" with its destination. Screen reader users cannot tell these are navigation links — they will be announced as "menu item" without destination information. For a language picker that *navigates*, `role="listbox"` / `role="option"` or simply a `<select>` element is more semantically appropriate, or the `role="menu"` layer should be dropped and the `<ul>` left as a plain list.

**Fix:** Remove `role="menu"` and `role="menuitem"` from the list and link elements, and change `aria-haspopup` on the trigger to something more accurate:
```astro
<ul class="lang-menu" data-lang-list hidden>
  {langCodes.map((code) => (
    <li>
      <a class="lang-menu-opt" href={translatePath(pathname, code)}
         data-lang-switch={code} hreflang={code} lang={code}
         aria-current={code === lang ? 'page' : undefined}>
```

### WR-03: `DiscordModal` `.dc-open-btn` is an `<a>` styled as a primary button — focus ring contrast insufficient

**File:** `src/styles/chrome.css:499-502`

**Issue:** The modal's "open Discord" action is an `<a>` element (`dc-open-btn`) with a white background and navy text. Its `:focus-visible` rule is:
```css
.dc-open-btn:focus-visible {
  outline: 2px solid var(--color-navy);
  outline-offset: 2px;
}
```
The `--color-navy` (#0a0c14) outline on a `--color-white` (#f0eae4) background is a dark outline against a light surface — that is fine for contrast. But the `outline-offset: 2px` means the 2px outline sits outside the element by 2px, over the `--color-navy-mid` (#10131e) modal background. A 2px navy outline against a near-black background is essentially invisible. WCAG 3.2.4 / 2.4.11 requires the focus indicator to have at least 3:1 contrast against adjacent colors.

**Fix:** Change the focus outline color to `var(--color-red)` or use a white outline with a thicker offset to ensure visibility against the dark modal background:
```css
.dc-open-btn:focus-visible {
  outline: 2px solid var(--color-red);
  outline-offset: 2px;
}
```

### WR-05: Chrome.ts `initNav` — scroll listener added on every `astro:page-load` but never removed; stacks across navigations

**File:** `src/scripts/chrome.ts:51`

**Issue:** `window.addEventListener('scroll', onScroll, { passive: true })` is called inside `initNav()`, which is called inside `init()`, which is registered on `document.addEventListener('astro:page-load', init)`. Because `init` is registered on `astro:page-load` (not just once), and `init` adds a new `window` scroll listener each time without removing the previous one, every navigation stacks another scroll handler on `window.scroll`. After 5 navigations, 5 separate `onScroll` handlers are running per scroll event, each toggling `.scrolled` and `.nav--hidden` on potentially stale nav element references. The comment in the file acknowledges the per-element stacking concern for modal triggers but misses that the scroll handler itself stacks.

**Fix:** Use a module-scoped flag or store/remove the scroll listener explicitly:
```ts
let scrollHandler: (() => void) | null = null;

function initNav(): void {
  if (scrollHandler) window.removeEventListener('scroll', scrollHandler);
  const nav = document.querySelector<HTMLElement>('[data-nav]');
  if (!nav) return;
  let lastY = window.scrollY;
  const onScroll = () => { /* ... */ };
  scrollHandler = onScroll;
  window.addEventListener('scroll', onScroll, { passive: true });
  onScroll();
}
```

### WR-06: Tailwind v4 `@theme` tokens `--color-red-soft` and `--color-white-muted` use `rgba()` — Tailwind v4 cannot generate utilities from these

**File:** `src/styles/theme.css:20` and `src/styles/theme.css:48`

**Issue:**
```css
--color-red-soft: rgba(192, 25, 44, 0.12);
--color-white-muted: rgba(240, 234, 228, 0.06);
```
Tailwind v4's `@theme` color system generates utility classes (`bg-red-soft`, `text-white-muted`, etc.) from color tokens — but it requires those tokens to be expressed in a format it can parse and modify (hex, `oklch()`, `hsl()`, `rgb()` with space-separated values). `rgba()` with a comma is not a valid `@theme` color value in v4's CSS-first system; v4 expects the raw channel values so it can apply opacity modifiers via `color-mix`. These two tokens will be silently skipped when generating utilities, meaning `bg-red-soft` and `bg-white-muted` (if used) will produce no output. The values work correctly as CSS custom properties (read by `var(--color-red-soft)` in component CSS), but their Tailwind utility counterparts are broken.

**Fix:** Express them as `oklch()` or bare hex with the appropriate opacity applied via `color-mix` syntax:
```css
--color-red-soft: color-mix(in srgb, #c0192c 12%, transparent);
--color-white-muted: color-mix(in srgb, #f0eae4 6%, transparent);
```

### WR-08: `choreography.ts` targets `.cards--summary .card` for tilt but the PackageCard component adds the `card--condensed` class, not `cards--summary`

**File:** `src/scripts/motion/choreography.ts:105`

**Issue:** The D-15 card tilt targets:
```ts
document.querySelectorAll<HTMLElement>('.cards--summary .card')
```
The `PackagesSummary.astro` component renders:
```astro
<div class="cards cards--summary">
  {t.tiers.map((tier) => <PackageCard condensed />)}
</div>
```
`PackageCard.astro` emits `<div class="card ... reveal">`. The parent has `.cards--summary`, so the selector `.cards--summary .card` should match. This is technically correct. However, the tilt is also applied via `card.classList.add('card--tilt')`, and `choreography.css` carries:
```css
.card--tilt {
  transform-style: preserve-3d;
  will-change: transform;
}
```
The problem is that under reduced-motion, `choreography.css` forcibly sets:
```css
.card--tilt { transform: none !important; will-change: auto; }
```
But `initChoreography()` gates on `if (prefersReduced ... ) return` before the tilt code runs, so `.card--tilt` is never added under reduced-motion. The `!important` override is therefore dead code that could silently suppress card hover transforms on non-tilt contexts if `.card--tilt` ever gets added by other means. Not a current bug, but a silent trap.

More critically, the `card.classList.add('card--tilt')` call is in `initChoreography()`, but `destroyChoreography()` does NOT remove the `.card--tilt` class from the elements. After a navigation away from the landing page and back, `card--tilt` from the previous session may or may not still be on the elements (depends on ClientRouter DOM behavior — full swap removes it; soft navigation may not). The tilt listener is re-added each time, potentially stacking on elements that already have it if ClientRouter preserves DOM state.

**Fix:** In `destroyChoreography()`, remove `.card--tilt` explicitly:
```ts
tilts.forEach(({ el, move, leave }) => {
  el.removeEventListener('pointermove', move);
  el.removeEventListener('pointerleave', leave);
  el.classList.remove('card--tilt'); // reset CSS state
  gsap.killTweensOf(el);
  gsap.set(el, { rotateX: 0, rotateY: 0 });
});
```

### IN-02: `sections.css` duplicates `.workflow-steps` rule (counter-reset)

**File:** `src/styles/sections.css:174-179` and `src/styles/sections.css:212-214`

**Issue:** `.workflow-steps` is declared twice: once at line 174 with `display: grid; gap: 0; border-top: ...` and again at line 212 with only `counter-reset: nocturna-step`. If someone adds a property to one block without checking the other, it can cause confusion about the canonical location for `.workflow-steps` rules.

```css
.workflow-steps {
```

### IN-03: `chrome.ts` `initNav` scroll handler closure captures the `nav` element but the `nav` may be `null` on pages without a nav

**File:** `src/scripts/chrome.ts:40-53`

**Issue:** The guard `if (nav)` wraps the scroll listener, so if `[data-nav]` is not found, no listener is added. This is correct. However, `init()` calls `initNav()`, `initLangSwitch()`, and `initDiscordModal()` unconditionally. `initLangSwitch()` calls `document.querySelectorAll('[data-lang-switch]')` and quietly iterates zero results if there is no switcher — that is safe. `initDiscordModal()` guards with `if (!overlay) return` — safe. `initNav()` guards with `if (nav)` for the scroll listener — safe. There is no practical problem, but the `init()` function re-runs after every navigation without cleanup of the nav's `lastY` closure variable, which is scoped per-call. Each navigation creates a fresh `lastY` starting at the current scroll position, which could cause a momentary scroll-direction jitter if the user navigates while mid-scroll. Low severity but worth noting.
